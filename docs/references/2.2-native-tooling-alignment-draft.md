## Answer: what exists, and did we duplicate it?

**There is functional overlap, but this inspection establishes no whole local module that can safely be replaced by a native command.** The native host owns extension installation, manifest semantics, compatibility, and update behavior. We already invoke that host for release installation tests. Our code additionally owns Usage Bridge's runtime allowlist and release evidence; these are different contracts.

The earlier idea of extracting a general validator and bundle builder needs narrowing. It would duplicate upstream capabilities if implemented indiscriminately. That proposed duplication has not yet been built.

**Updated host direction (2026-10-04):** Use the newest stable Spec Kit as the primary development and current-host target, rather than designing against the existing `v1.0.12` test pin. GitHub's live release API reports [v1.1.0](https://github.com/github/spec-kit/releases/tag/v1.1.0), published 2026-10-02, resolving to `f1d3a4f8337ebbd3ae22760a9c12e3352b93a175`. Its source confirms native `extension update`, the `SPECKIT_CATALOG_URL` override, manifest schema `1.0`, and Python 3.11+. Retain older-host coverage only to honor the existing minimum-support contract; it must not constrain the primary design silently.

## Proposed 2.2 changes

### 1. Establish the supported native contract before deleting code

Inspect the newest stable host release and record which public commands and failure behaviors are available. Compare unreleased source where it offers relevant functionality. Use an isolated developer environment; stable v1.1.0 requires Python 3.11+, independently of Usage Bridge's Python 3.9 runtime support. Any old-host lane is compatibility verification, not the design baseline.

For each candidate deletion, document the local check, its callers, the native replacement, the host revisions that support it, and when the replacement runs. If the native check runs only during installation, it does not replace an offline publication/download verification gate. If equivalence is not demonstrated, keep the local check and describe its purpose accurately.

Expected result: a short ownership map in existing release documentation, not another validation framework or dependency on private `specify_cli` APIs.

### 2. Make native installation evidence explicit

Trace [`release-pipeline.yml`](../../.github/workflows/release-pipeline.yml), [`orchestration.py`](../../tools/release/orchestration.py), [`release_fixtures.py`](../../tests/release_fixtures.py), and [`test_release_install.py`](../../tests/integration/test_release_install.py) together. Preserve the existing use of the downloaded, attested release archive via `UB_RELEASE_ARCHIVE`.

Add the smallest meaningful negative integration case proving that the chosen host rejects a malformed extension manifest in the supplied archive. Create the malformed fixture outside the checkout; do not alter the production manifest. Assert a nonzero native command result and absence of a successfully registered extension. Select the malformed field only after checking the pinned host's behavior.

Inspect existing evidence before adding fields. The fixture currently writes a small local `release-verification.json` with host ref and archive name; this alone is not a signed or complete release proof. The release pipeline has separate source/digest/job evidence. Extend or clarify that established chain only if a concrete gap is demonstrated, avoiding a competing evidence format or duplicate hashing system.

### 3. Distinguish forced reinstall from a real versioned update

The current `test_upgrade_preserves_config_and_reports` reinstalls the same archive using native `extension add --force`. That is useful preservation coverage, but its name overstates what it exercises.

Proposed change: rename/document it as forced-reinstall preservation. Add one genuine old-to-new `specify extension update` regression using the newest stable host's public catalog/update interface and two valid fixture archive versions. Keep catalog serving local, preserve user configuration and reports, and prove the installed version actually changes. Source inspection confirms the catalog override in v1.1.0; executable behavior still needs validation. Assess the existing minimum-host lane separately and record any incompatibility instead of labeling another forced reinstall an upgrade test.

Reuse the existing HTTP server and install helper where they fit. Do not write a local updater or add generalized test adapters to simulate native success.

### 4. Make host-matrix claims accurate

The release workflow currently defines `host: [minimum, current]` but gives both jobs `UB_SPEC_KIT_REF: v1.0.12`. Those labels provide no distinct-version evidence today.

The user has selected newest stable as the current target. Map the existing minimum lane to `v1.0.12` while that support contract remains in force, and the current lane to the verified newest stable (`v1.1.0` at this check). Keep workflow refs and evidence reporting consistent. An optional development-source experiment may use the resolved `main` SHA; do not count it as stable-version evidence or add a mandatory fifth/sixth gate without a design decision.

Before changing job labels or counts, inspect evidence collection and required-check expectations. If separate named lanes are a release requirement, preserve them and document their identical pins until policy changes. Add a focused regression only for any changed mapping/evidence behavior; do not silently weaken the publication gate.

### 5. Document responsibility and terminology

Update [`docs/release.md`](../release.md) and related research where needed:

- Native host acceptance covers supported extension semantics; Usage Bridge tests cover its actual installed behavior.
- Local packaging enforces a product-specific runtime allowlist, required legal/vendor files and reproducible extension archives.
- Local verification binds published bytes, source SHA, metadata, checksums, attestations and candidate history.
- “Extension archive,” “bundled extension,” and “Spec Kit bundle” name different artifacts.
- Community submission is an explicit producer action; upstream owns intake and catalog review. Neither installation nor prerelease publication should imply submission.

## Checks that must remain

Retain path/link protections, compressed/expanded/member limits, exact member allowlists, vendor provenance, asset hashes, tag/source binding, immutable retry verification, historical-candidate verification, protected publication boundaries and explicit submission gates. Preserve installed-runtime checks for checkpoint, capture, report and check commands. Host installation success does not prove product behavior or release provenance.

An identical low-level technique, such as SHA-256 or deterministic ZIP ordering, is not sufficient reason to couple our release verifier to upstream private helpers. Prefer existing local helpers and the standard library when public host commands cannot fulfill the same contract.

## Outside this cycle

Do not extract a separate toolkit repository, add reusable cross-repository workflows, implement `bundle.yml` support, change built-in extension workflows upstream, or introduce a generic adapter/plugin system. Do not copy the upstream validator. Built-in wheel verification remains a future pilot described in the research draft.

Do not publish, change live repository settings, create upstream issues, or commit/push as a side effect of this draft. This file requests design work for a later cycle, not execution now.
